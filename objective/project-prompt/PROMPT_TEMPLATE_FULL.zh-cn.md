# 提示词模板 · 完整版（给编码 Agent）

> 适合较大 / 较复杂的项目。复制「模板」部分填空后发给能改文件、能跑命令的编码 Agent。
> 给 Agent 的提示词里，**边界和验收比"怎么实现"更重要**：你说清"要什么、别越界、怎么算完成"，实现交给它。

---

## 填写要点（先看这几条，再填模板）

1. **给真实例子，别只给描述。** 一个输入/输出样例 > 三段抽象话。
2. **验收标准要可验证。** 不要写"做好一点"；写"运行 `pytest` 全过""处理 1 万行 < 2 秒"。
3. **边界写死。** 范围 + 权限 + 停止条件 + 何时求助——这四样防止 Agent 帮倒忙。
4. **先计划后执行。** 大任务让它"先给计划、我确认、再动手"，省得跑偏。

# 验收标准（怎么算完成）
- [ ] 能 <运行命令 / 通过测试 / 满足指标>
- [ ]

# 边界与协作方式（给 Agent 的行为约束）
- 改动范围：只允许修改 <目录/文件>，不要动 <哪些>。

---

## 关于「能力边界」怎么定

能力边界 = **范围 + 权限 + 停止条件 + 何时求助**，都要显式写进上面的「边界与协作方式」：

| 边界类型 | 怎么写 |
|---|---|
| 范围边界 | "只改 `src/` 下的文件，不要动 `config/`" |
| 权限边界 | "不要执行删除、不要 push、不要改 git 配置" |
| 停止条件 | "做完 X 就停下来问我，不要自动继续做 Y" |
| 求助边界 | "遇到不确定的设计选择，先问我再动手" |
| 验证边界 | "每改一处就跑一次测试，失败就停" |

另外记住 LLM 天然的弱点：不知道你的私有/最新信息、会编造不存在的 API、长链条计算易错。
应对：给真实资料、要求"不确定就说不确定，不要猜"、让它分步做。
