# 项目历史

## 项目概述
- `feature-spec` 是一个可复用的 Skill，用于将非正式功能需求或项目级需求整理成供另一个编码 AI 实施和验证的需求。
- 它不绑定特定技术栈，适用于 Python、Go、Bash 和嵌入式固件等项目。

## 设计与关键决策
- 中文需求，包括“整理需求”，也应触发此 Skill。生成的规格书默认使用用户的语言，除非用户另有指定。
- Skill 区分已确认事实、建议和未知事项；不编造项目细节，也不编写实现代码。
- 规格书涵盖可观察行为、相关非功能需求、验收标准、验证方案，以及简短且注明来源的调研结论。
- 项目级需求先整理成拆分清单，记录整体目标、共享约束、边界明确的工作项、完成条件及已知依赖。每份单项详细规格书仍只描述一个边界明确的变更。
- 项目拆分回答“交付什么”；可选的推荐阶段只按已知依赖为现有工作项 ID 分组，说明建议执行顺序和完成条件，不重复详细需求，不臆造优先级、工期或工作项。所有工作项互相独立或只有一个工作项时，不分阶段；依赖未决问题的工作项标为 `Blocked`。用户之后可任选工作项单独细化，不必先遵循阶段。
- P0 定位为可随时开展、可重复进行的原型与参考轨道，不是按依赖排序的阶段，也不是 Phase 1 的必经前置步骤。P0 可以验证可行性、搭建端到端骨架，或生成供后续参考的粗略功能实现。Skill 负责规定 P0 工作，原型代码由另一个编码 AI 实现。
- 面向整体功能的参考原型应以最小深度覆盖主流程与模块边界，再按需深入验证不确定的功能。源 Skill 草稿区分文档核实（V0）、真实环境中的最小探针（V1）、接入骨架（V2）、与用户确认的目标对比测量（V3），以及粗略功能实现。P0 交付物应说明验证目标、允许的捷径、代码去留、证据、假设和遗留缺口。
- P0 代码本身不确认需求，也不取代获批准的正式实现。其范围内已确认的核心业务规则必须得到遵守，或明确标为未覆盖；其他行为在用户接受前仍属建议或假设。
- 默认在对话中返回规格书或项目拆分。若用户要求保存且当前模式允许写入，优先遵循项目现有文档约定；否则拆分清单建议保存至 `<project-root>/docs/specs/<project-slug>-breakdown.md`，单项规格书建议保存至 `<project-root>/docs/specs/<feature-slug>.md`。只创建实际保存文档所需的目录，不预先初始化文档骨架。
- 用户明确提出或确认的核心业务规则，未经用户对具体变更方案明确批准不得修改。需求整理 AI 与实现 AI 都必须遵守；技术冲突须指出依据和影响、提出选项并等待决策，未决部分阻塞，独立工作可继续。规格书和项目拆分必须携带规则 ID、来源、决策状态及给实现 AI 的停工约束；代码与规格不一致本身不构成改写规则的授权。
